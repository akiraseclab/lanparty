# lanparty 流量走向白皮书 —— 数据包到底是怎么走的

> 读者对象：想搞懂"我打的每一帧游戏数据到底去了哪"的普通用户
> 所有结论都有实测依据，抓包证据见第 5 章。日期：2026-09-06

---

## 1. 三张总图：你的游戏流量只有三种走法

### 走法一：直连型游戏（饥荒、MC、泰拉瑞亚……有人当主机，其他人填 IP 连）

```
没有 lanparty：   朋友 ──填主机的公网IP──► 主机（需要主机有公网IP或端口映射，多数家庭没有 → 连不上）

有 lanparty：     朋友 ──填主机的虚拟IP(10.66.0.x)──► 自己的虚拟网卡
                        └─► 加密隧道 ──► 你的服务器中转 ──► 主机的虚拟网卡（100% 走通，不依赖宽带环境）
```

### 走法二：Steam 匹配型游戏（渔力全开、怪猎……游戏内点邀请自动连）

Steam 会替你们选路，候选有三条，**按它自己的标准择优**：

```
① LAN route（局域网路由）  双方在同一个二层网络（比如都插着 lanparty 虚拟网卡）
② direct route（直连路由） 双方公网地址直接打通（UDP 打洞）
③ relay route（中继路由）  打洞失败 → 绕 Valve 海外中继网（SDR）→ 卡的元凶
```

**关键认知**：这三条路是 Steam 挑的，不是你挑的。lanparty 能做的是把"①"变成一条
优质候选路，但 Steam 仍可能选"②"（能通就用）。这就是"进网了但游戏流量没走隧道"
的原因——不是网坏了，是 Steam 没选它。确定性接管要等 v0.2（见第 7 章）。

### 走法三：官方专用服务器游戏（CS2、Dota2、绝大多数网游）

你连的是厂商服务器，和 P2P 组网无关。lanparty 帮不上忙（除非你把发往那台
服务器的路由手动指进隧道——这正是商业加速器做的事，v0.3 展望）。

## 2. 三十分钟看懂四个基础概念

- **路由表**：你电脑的"快递分拣规则"。发一个包时，系统查表决定它从哪个网卡出去。
  lanparty 接入时会添加一条规则：`10.66.0.0/24 → 从 lanparty 虚拟网卡走`。
  这就是"发往队友虚拟 IP 的包会进隧道"的全部原理。
- **TUN 虚拟网卡**：一块"假网卡"，没有物理网线，另一头连着 lanparty 进程。
  系统把 IP 包递给它 → lanparty 进程读到 → 加密发往服务器；反向同理。
  它是所有虚拟局域网软件（蒲公英/ZeroTier/EasyTier/我们）的共同地基。
- **NAT**：家庭宽带的"多人共用一个门牌号"机制。它让你能上网，但让外面的人
  主动连你变得困难——P2P 联机的所有麻烦都源于此。
- **广播**：向"本子网所有人"喊话（目标地址 255.255.255.255 或 10.66.0.255）。
  游戏的"局域网搜索"靠它喊话找人。lanparty v0.1.1 起支持跨隧道转发广播。

## 3. 一个 ping 的完整旅程（lanparty 内部，共 9 步）

以"朋友(10.66.0.4) ping 你(10.66.0.3)"为例：

```
1. 朋友敲下 ping 10.66.0.3，系统查路由表 → 交给 lanparty-t1 虚拟网卡
2. 朋友的 lanparty 进程从虚拟网卡读到这个 ICMP 包（此刻是明文）
3. 用会话密钥 AES-256-GCM 加密，装进"帧"，写入与服务器之间的 TCP 隧道
4. 包穿越公网到达你的服务器（这一段的延迟 ≈ 朋友到服务器的物理距离）
5. 服务器解密 → 查成员表：10.66.0.3 是谁 → 重新加密 → 写入与你的隧道
6. 包穿越公网到达你的电脑（延迟 ≈ 服务器到你的物理距离）
7. 你的 lanparty 进程解密 → 写入 lanparty-t0 虚拟网卡
8. 系统协议栈收到 ICMP 请求，生成回应包
9. 回应包沿原路（8→1 的逆序）回到朋友屏幕上
```

**总延迟 ≈ 你到服务器 + 服务器到朋友 + 每跳加解密的微秒级开销。**
这就是为什么服务器位置和线路质量比 CPU 配置重要得多。

## 4. Steam P2P 的三条路是怎么选的（协议层）

依据：[Steamworks 官方文档](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay)、
[Steamworks SDK v1.44 更新公告](https://steamcommunity.com/groups/steamworks/announcements/detail/1791775741704351698)
（首次引入 SteamNetworkingSockets，明确描述 direct/relay 路由评估与 LAN 路径检测）、
[Valve 开源的 GameNetworkingSockets 源码](https://github.com/valvesoftware/gamenetworkingsockets)
（路由打分逻辑就在里面，可自行研读）。

1. 双方通过 Steam 后台交换候选地址（本地/内网地址 + 预测的公网映射地址）；
2. 同时探测多条路径，估算各自的 RTT 与丢包；
3. **择优录取**：通常直连 > 中继，但新版 Steam"连通性优先"——打洞失败时果断走
   SDR 海外中继，同子网也不保证走本地路径；
4. 会话建立后**不再换路**。所以：先开 bat 入网 → 再完全重启游戏 → 才有机会让
   Steam 重新选路。

## 5. 实测证据：同一个 ping，网卡内侧 vs 隧道外侧（2026-09-06 服务器实抓）

在服务器上用双网络命名空间搭建"两台真实机器"，ping 时携带特征串
`lanparty`（hex `6c 61 6e 70 61 72 74 79`），同时在两个位置抓包：

| 抓包位置 | 看到的内容 | 特征串出现次数 |
|---|---|---|
| **虚拟网卡内侧**（lanparty-t0，游戏视角） | 明文 ICMP，特征串清晰可见 | **2 次** ✔ |
| **隧道外侧**（vethA-root，公网视角） | 只有发往 coord:17802 的 TCP，载荷是不可读的密文块 | **0 次** ✔ |

外侧抓包样例（`6568 2027 c05d 2dc5` 这类就是 AES-256-GCM 密文 + 16 字节校验标签）：

```
04:14:59 IP 192.168.100.2.49212 > 192.168.100.1.17802: Flags [P.], length 109
	0x0000:  4500 00a1 e09f 4000 4006 1063 c0a8 6402
	0x0010:  c0a8 6401 c03c 458a 6568 202b c05d 2dc5
	0x0020:  8018 01f6 49e8 0000 0101 080a 507c 0a44
```

结论：**游戏在网卡内侧说"普通话"，出了网卡就是只有协调节点能解的"密语"；
协调节点是唯一能看到明文的位置（它必须解密才能转发），这也是 README 安全声明的由来。**

## 6. 为什么昨晚渔力全开"没效果"（复盘）

1. 你们入网时间线有缺口（中途掉线重连过），游戏会话建立时可能一方不在网；
2. Steam 会话建立后不换路，旧会话继续走老路径；
3. 最根本的：Steam 择优时认为公网直连"够好"，没选局域网候选。

**对策**（按优先级）：① 先开 bat 再完全重启游戏；② 用饥荒这类直连游戏验证网络
本身；③ 真正的根治是 v0.2"公网 IP 劫持"——不管 Steam 选哪条路，发往队友公网
IP 的包都会被强制导进隧道（设计见 [v0.2-steam-p2p-design.md](./v0.2-steam-p2p-design.md)）。

## 7. 自己动手观察流量的工具箱

| 想知道什么 | 工具 | 怎么用 |
|---|---|---|
| 谁在虚拟网里 | 各自的黑窗口 | 窗口里会实时打印成员列表和 vip |
| 隧道是否有流量 | 服务器上 `ss -tni sport = :7800` | 隔几秒采样两次，对比 `bytes_sent/received` 是否增长 |
| 哪个程序在连谁 | Windows 资源监视器 → 网络 | 按进程看远程 IP；游戏连的若是队友公网 IP = 没走隧道 |
| 链路上到底传了什么 | 服务器 `tcpdump -i any port 7800 -X` | 应该只能看到不可读的密文块（见第 5 章样例） |
| 游戏实际连了谁 | Wireshark 过滤游戏进程的 UDP | 对照队友的公网 IP 和虚拟 IP 就知道走的哪条路 |
