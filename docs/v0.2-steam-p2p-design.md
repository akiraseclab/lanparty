# lanparty v0.2 设计草案：让 Steam P2P 游戏确定性走 lanparty

> 日期：2026-09-05 ｜ 前置调研：Steam 联机协议 + 今晚渔力全开实测（流量未走隧道）

## 1. 背景与问题

v0.1 的虚拟局域网对"能填 IP 直连"的游戏（饥荒/MC/泰拉瑞亚）完全有效；但对
Steam P2P 匹配类游戏（渔力全开、怪猎等）只是"提供候选路径"——实测渔力全开
在双方均在网的情况下，游戏流量仍走了公网路径，隧道内只有心跳。

根因（Steam 联机协议，见参考）：

```
候选收集（本地/内网地址 + 预测公网映射地址）
   → UDP 打洞（Steam 后台牵线，同时向预测地址发探测）
   → 失败则回退 SDR 海外中继（卡顿根源）
```

新版 Steam"连通性优先于就近"：同子网不保证走本地路径，是否选用内网候选
取决于游戏使用的 API 与客户端版本，**不可控**。

## 2. 方案对比

| 方案 | 原理 | 可控性 | 工程量 | 结论 |
|---|---|---|---|---|
| A. 同子网候选（v0.1 现状） | 赌 Steam 选用内网候选 | ❌ 不可控 | 0 | 保留，但不是答案 |
| **B. 公网 IP 劫持（选定）** | 把"发往队友公网 IP"的流量导进隧道并改写目标为虚拟 IP | ✅ 强制 | 中 | **v0.2 核心** |
| C. 进程级全接管 | 商业加速器模式：按进程把全部流量导入隧道 | ✅ 最强 | 大（需 WFP/驱动） | v0.3 展望 |

## 3. 方案 B 设计

### 3.1 数据来源

协调节点天然知道每个成员的公网 IP:Port（TCP 控制连接的来源地址）。
新增机制：成员表里携带 `public_ip`，随 MEMBERS 帧分发给所有人。

### 3.2 数据路径

```
Steam 让游戏连 朋友的公网IP 39.182.7.45:port
  → 你的电脑：路由 39.182.7.45/32 dev lanparty（peer 收到成员表后自动添加）
  → 包进入 TUN → peer 识别 dst=39.182.7.45 是队友公网 IP
  → 改写 dst 为其虚拟 IP 10.66.0.12（DNAT），从隧道发出
  → 朋友的 peer 收到（src 已是虚拟网内地址），正常交付
  → 回程对称：朋友的包 dst=你的公网IP → 改写 → 隧道回来
```

效果：Steam 以为直连成功，实际全程经你的服务器中转，永不再绕 SDR。

### 3.3 实现要点

- **公网 IP 获取**：coord 从 TCP 对端地址直接取（已有）；注意 NAGLE 级细节——
  成员重连后公网 IP 变化要触发成员表重新广播；
- **Windows 端 DNAT**：用户态网络栈实现。复用 wireguard-go 自带的
  `golang.zx2c4.org/wireguard/tun/netstack`（gvisor），或自写最小 NAT44
  （仅处理 ICMP/UDP/TCP 头改写 + 连接跟踪）。优先评估 netstack；
- **Linux 端**：可用 iptables/nftables DNAT（peer 建卡时自动下发规则）；
- **路由管理**：peer 收到成员表后，对每个队友的公网 IP 添加 /32 路由进 TUN
  （Windows `route add`，Linux `ip route`），离线时撤销；
- **边界情况**：两个成员公网 IP 相同（同一 NAT 后）→ 无需劫持，直连虚拟网内
  地址即可（本就同子网）；游戏流量本身打洞成功的场景会被劫持"降级"为中转，
  属可接受代价（中转就在国内服务器）；
- **开关**：默认开启，配置项 `p2p_hijack: true/false` 可关。

### 3.4 一并纳入 v0.2

- **广播/组播转发**（解决饥荒"局域网列表"搜不到、部分游戏 LAN 发现失效）：
  peer 收到 dst 为子网广播地址的包时，向同网所有成员复制转发（注意防环：
  只转发来自隧道的，TUN 收到的广播复制后打隧道标记）；
- **虚拟 IP 记忆**：coord 按成员名记住上次分配的 IP，重连不变（现在每次重连
  IP 会递增，体验差且容易填错 IP）；
- **Windows 免管理员方案调研**（wintun 必须管理员，考虑服务化安装一次）。

## 4. 里程碑
